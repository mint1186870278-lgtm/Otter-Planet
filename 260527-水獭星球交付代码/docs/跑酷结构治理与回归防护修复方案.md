# 跑酷结构治理与回归防护修复方案

记录日期：2026-07-04

## 背景

本方案基于当前代码评价和现有文档重新整理。核心判断是：当前问题不是某一个按钮、某一个 loader、某一颗星星单点写错，而是跑酷段已经出现了“多个 owner 同时控制同一件事”的结构性冲突。

这次修复目标不是继续在 `SectionParkour.tsx` 里补更多判断，而是先把控制权、生命周期、兜底、验证方式拆清楚，再按小步执行。

已遍历参考文档：

```text

docs/3D模型压缩优化方案-Meshopt优先.md
docs/3D模型压缩基线记录.md
docs/跑酷地形低模首包-CDN落地记录.md
docs/跑酷静态地形NavMesh优化方案.md
docs/跑酷静态地形HeightField-NavMesh改进执行方案.md
docs/跑酷部署回归问题修复方案-加载同步与星星布点.md
deploy/packages/20260704-terrain-delay/README.md
docs/visual-novel-roadmap.md
docs/visual-novel-step-status.md
```

## 当前结论

### 1. 现在最大风险是控制权冲突

同一件事被多个地方判断和推进：

```text
跑酷是否进入：
App.tsx / scroll-snap / SectionIntro / SectionParkour

加载页是否消失：
public/otterlantis-loader.js / ParkourLoading / SectionParkour / ParkourScene

场景是否 ready：
DOM 查询 canvas / DOM 查询教学按钮 / R3F 首帧 / 低模地形 / 完整地形

星星到底有哪些：
STAR_POSITIONS / debugLandStars / activeLandStarItems / creekStars / interactionHints
```

这会导致一个表现：某个补丁在本地看起来解决了问题，但部署后换一个网速、缓存状态、加载顺序，就又出现“第一次按方向跳回开头”“loader 提前消失”“星星引导指错位置”。

### 2. React 和全局 JS 的边界不清

`public/otterlantis-loader.js` 是全局命令式脚本，`App.tsx` 和 `SectionParkour.tsx` 是 React 状态流。现在两边都在影响加载页：

```text
React 渲染 fallback -> 全局 loader start
全局脚本监听资源 -> 改进度
React 场景 ready -> 全局 markSceneReady
全局 overlay 是否存在 -> 又影响 loader start
```

合理边界应该是：

```text
React 拥有业务状态和场景 ready 判断。
全局 loader 只负责显示进度和接收显式事件。
全局 loader 不再通过 DOM 猜测场景是否 ready。
```

### 3. `SectionParkour.tsx` 职责过重

当前 `SectionParkour.tsx` 同时负责：

```text
页面进入和 scroll 行为
加载页同步
键盘教学
玩家输入
NPC 对话
星星收集
调试面板
月亮演出
完整地形延迟加载
R3F Canvas 编排
```

这会让任何小修都容易碰到无关逻辑。后续不建议继续在这个文件里堆大块逻辑，应按 owner 拆成 hook 和小模块。

### 4. 兜底分散且不可验证

现有文档已经提到很多 fallback：

```text
低模地形 fallback
完整地形延迟加载
HeightField fallback 到 raycast
loader 慢网提示
ErrorBoundary
CDN / 源站 fallback
```

但这些兜底没有统一状态表，也没有自动回归验证。结果是“有兜底代码”，但不容易确认兜底是否真的在正确时机生效。

### 5. 文档和交付物混在一起

原先 `docs/deploy-20260704-terrain-delay/package` 里放了构建产物快照：

```text
package/index.html
package/assets/*.js
```

这类文件对临时部署有用，但放在 `docs/` 会污染人读文档的结构。后续建议把发布包、部署快照、真实文档分开。

## 总原则

### 一个 owner 只管一件事

```text
App.tsx:
只管大 section 流转，不判断 3D 场景内部 ready。

SectionParkour.tsx:
只管跑酷业务状态组合，不直接堆所有副作用。

ParkourScene.tsx:
只发出 3D 场景生命周期事件，不控制页面滚动和全局 loader。

public/otterlantis-loader.js:
只显示进度，不猜 DOM，不决定场景是否 ready。

StarPlacement:
只管实际渲染星星列表，收集、引导、障碍避让都读同一份 active star 数据。
```

### 先复现，再修复

每个 P 阶段开始前先记录复现方式：

```text
正常网络
Chrome Fast 3G
Chrome Slow 3G
清缓存首访
二次访问
快速连点进入跑酷
第一次方向键 / 第一次方向按钮
```

没有复现记录，不继续加补丁。

### 状态机优先，UI 其次

先定义状态，再让 UI 跟着状态渲染。不要反过来用 DOM 是否存在来推导状态。

跑酷进入状态建议收敛为：

```text
idle
approaching
routeMounted
loadingShell
shellReady
tutorialActive
playing
completed
failed
```

加载状态建议收敛为：

```text
inactive
moduleLoading
shellLoading
shellReady
visualReady
fullTerrainLoading
fullTerrainReady
slowNetwork
failed
```

## 截图评价对应修复表

| 评价问题 | 对应原因 | 修复动作 |
|---|---|---|
| 太乱 | `SectionParkour.tsx` 混合太多职责 | P2 拆 hook 和 owner 模块 |
| 结构性差 | 没有明确状态机和 owner | P1 先写 owner map 和 ready contract |
| 文档/结构不给人看 | docs 混入部署包和过宽方案 | P4 建 docs index，移动部署快照 |
| 防护不好 | fallback 分散，没有统一验收 | P3 加 slow/error/low-mode 验收 |
| 没兜底 | 有代码但缺状态化兜底入口 | loader 加明确 slowNetwork / failed / lowMode |
| 相互冲突 | React、loader、DOM 查询都能 complete | loader 只接受显式 markSceneReady |
| React 和 JS 来回控制 | 全局脚本和 React 双向推状态 | 改成 React -> loader 单向桥接 |
| 生命周期没清理 | window 监听、timer、scroll lock 分散 | 每个 hook 必须返回 cleanup |
| 回归没验证 | 依赖人工体感 | 加 Playwright / Network / 单测 |
| 少补丁，多归因 | 之前常直接改现象 | 每阶段先写复现、原因、验收、回滚 |

目标：避免在当前脏工作树上继续叠补丁。

当前工作树已有未提交改动：

```text

src/components/DirectionTutorialOverlay.tsx
src/components/ParkourScene.tsx
src/components/SectionParkour.tsx
src/components/parkourConstants.ts
```

执行动作：

```text

2. 对每个文件做 diff 审查，标记：
   - 已验证可保留
   - 临时补丁需重做
   - 风险较高需回滚或重写
3. 运行一次基线：
   npm run lint
   npm test

4. 录一份当前问题复现记录：
   - 首次进入跑酷 loader 是否同步
   - 第一次方向输入是否跳回开头
   - 教学阶段是否请求 scene-terrain-opt.glb
   - 陆地星星是否至少可见 12 颗
```

验收：

```text

知道哪些改动是稳定的，哪些只是临时补丁。
```

## P1：重建 owner map 和 ready contract

目标：先把“谁说了算”定下来。

### 1. 跑酷入口 owner

新建或整理：

```text
src/hooks/useParkourRouteLock.ts
```

职责：

```text
1. intro -> parkour 滚动期间锁住跨 section 输入。
2. parkour 教学 active 时阻止 scroll-snap 抖动。
3. 离开跑酷或进入 playing 后恢复页面滚动。
4. 所有 wheel / touchmove / keydown 监听必须 cleanup。
```

`App.tsx` 只负责：

```text
scrollToSection(3)
把 containerRef 交给 useParkourRouteLock
```

### 2. 加载页 owner

新建或整理：

```text
src/hooks/useParkourLoadingLifecycle.ts
```

职责：

```text
1. start loader
2. 接收 ParkourScene ready event
3. 管理 slow / verySlow / failed
4. 只在 shellReady + visualReady 后 markSceneReady
5. 卸载时清 timer
```

删除这类逻辑：

```text
querySelector('canvas')
querySelector('[data-tutorial-direction]')
DOM 出现就 ready
render 阶段调用 window.otterParkourLoading.start()
```

### 3. 3D 场景 owner

`ParkourScene.tsx` 只上报事件：

```ts
onShellReady()
onVisualReady()
onFullTerrainReady()
onSceneError(error)
```

建议 ready 条件：

```text
shellReady:
Canvas 创建、灯光、低模地形、主角或主角占位、星星系统、教学 UI 都已 mount。

visualReady:
R3F 至少完成 2 帧，避免只出现蓝色背景。

fullTerrainReady:
完整 scene-terrain-opt.glb 下载并渲染完成。
```

加载遮罩第一版只等：

```text
shellReady + visualReady
```

不等待 `fullTerrainReady`，否则又会被 35.61 MB 地形拖慢。

### 4. 全局 loader owner

`public/otterlantis-loader.js` 只保留：

```text
start()
markModuleLoaded()
markSceneReady()
markFailed(reason)
getState()
```

禁止：

```text
通过 DOM 猜测场景 ready
自动 completeScene()
根据 canvas/tutorial 是否出现决定隐藏
```

允许：

```text
统计 XHR/fetch 资源进度
进度最多显示到 96 或 98
收到 markSceneReady 后补到 100 并淡出
慢网时显示明确提示
```

验收：

```text
1. loader 隐藏只有一个正常入口：markSceneReady。
2. React -> loader 是单向桥接。
3. 全局 JS 不再反向决定 React 业务状态。
```

## P2：拆 `SectionParkour.tsx`，收敛副作用

目标：减少一个文件里同时控制所有事。

优先拆出：

```text
src/hooks/useControlTutorialFlow.ts
src/hooks/useParkourInput.ts
src/hooks/useParkourLoadingLifecycle.ts
src/hooks/useParkourRouteLock.ts
src/hooks/useActiveStars.ts
src/hooks/useParkourCutscenes.ts
```

推荐边界：

```text
useControlTutorialFlow:
只管方向教学步骤、正确输入、完成回调。

useParkourInput:
只管 keysHeld、velocityRef、pointer drag、window listeners。

useActiveStars:
只返回实际渲染和可收集的星星列表。

useParkourLoadingLifecycle:
只管 routeSceneReady / slowNetwork / markSceneReady。

useParkourCutscenes:
只管 fakeMoon / realMoon / freeze 状态。
```

每个 hook 的硬要求：

```text
1. 有明确输入参数。
2. 有明确返回值。
3. window/document 监听必须 cleanup。
4. timer 必须 cleanup。
5. 不直接 query DOM，除非它的职责就是桥接第三方 DOM。
```

验收：

```text
SectionParkour.tsx 行数明显下降。
输入、加载、星星、过场的逻辑可以分别测试。
```

## P3：星星数据统一和可达性修复

目标：星星视觉、收集、引导、障碍避让全部读同一份 active 数据。

新建或整理：

```text
src/components/parkour/starPlacement.ts
```

提供：

```ts
getBaseLandStars()
getActiveLandStars(debugOverrides)
getCollectibleStars({ includeCreek })
assertStarPlacement(stars)
```

规则：

```text
1. 陆地星不少于 18 颗，建议 21 颗。
2. TOTAL_STARS 仍保持 9，不改变剧情节奏。
3. 前 30 秒主路径内能自然看到至少 3 颗。
4. 沿主路径不绕路能看到至少 12 颗。
5. 新增星星 id 不得和水面星 20-28 冲突。
6. 引导、收集、障碍避让、debug 面板全部使用 activeLandStarItems。
```

需要修正的点：

```text
findNearestUncollectedStar 不再直接吃 STAR_POSITIONS。
focusStarId / guidedStarId 必须指向实际渲染星。
Obstacles 避让也必须使用同一份 active stars。
```

验收：

```text
1. assert 无重复 id。
2. assert 至少 18 颗陆地星。
3. 任意收 9 颗可通关。
4. 不收水面星也能通关。
5. 星星不埋地、不悬空、不被树挡死。
```

## P6：性能与 CDN 放到行为稳定后

当前仍然保留性能路线：

```text
低模首包
完整地形延迟加载
HeightField / NavMesh
低模 camera occluder
CDN / 对象存储
真拆地形包
```

但执行顺序要调整：

```text
先稳定进入、loader、星星。
再做 CDN 和真拆包。
```

原因：

```text
CDN 可以改善下载速度，但不能修复第一次方向输入跳回开头。
真拆地形包会增加更多 ready 状态，如果当前 ready contract 不稳，会让问题更复杂。
```

CDN 阶段验收：

```text
1. VITE_OTTERLANTIS_ASSET_ORIGIN 指向 CDN 后，GLB 请求 host 正确。
2. GLB / bin / webp / m4a 有长期缓存和 Accept-Ranges。
3. index.html 不强缓存。
4. 清缓存首访和二次访问都记录 Network 瀑布图。
```

## 不建议现在做

```text
1. 不继续在 SectionParkour.tsx 里追加大段临时 if。
2. 不让 public/otterlantis-loader.js 继续 query DOM 判断 ready。
3. 不把角色贴地重新切回 HeightField，出生点刚恢复正确，先不要碰。
4. 不用 CDN 掩盖状态流问题。
5. 不在 docs 里继续放构建后的 JS chunk。
```

## 建议执行顺序

```text
P0：冻结现场，审查当前 6 个未提交文件，记录复现。
P1：owner map + ready contract，先解决 React/JS/DOM 三方冲突。
P2：拆 SectionParkour 副作用，清理生命周期。
P3：统一星星 active 数据，修星星可达和引导。
P4：补单测、Playwright、Network 验证。
P5：整理 docs 和 deploy 目录。
P6：行为稳定后继续 CDN / 真拆地形包。
```

## 最小可执行切片

如果只先做一小步，建议先做：

```text
1. 保留当前能跑的逻辑。
2. 新增 useParkourLoadingLifecycle。
3. 删除 DOM ready 猜测。
4. ParkourScene 显式发 shellReady + visualReady。
5. loader 只接受 markSceneReady。
6. 加一个 Playwright 或手动 Network 验收记录。
```

这个切片能直接解决“加载页和场景不同步”的根因，也能顺手把 React 和全局 JS 的边界定下来。

## 最终验收清单

功能：

```text
1. 第三页进入跑酷后，第一次方向输入不跳回首页或开头。
2. loader 只在低模可玩首帧真实出现后淡出。
3. 慢网下 loader 不会卡死在某个数字且无解释。
4. 完整地形未加载完成时，低模场景仍可玩。
5. 完整地形加载失败时，主流程仍可继续。
6. 陆地星星可见、可达、数量有冗余。
7. 出生点保持当前正确位置。
```

工程：

```text
1. npm run lint 通过。
2. npm test 通过。
3. npm run build 通过。
4. SectionParkour 不再继续承担所有副作用。
5. loader ready 没有 DOM query 猜测。

```

人工测试：
