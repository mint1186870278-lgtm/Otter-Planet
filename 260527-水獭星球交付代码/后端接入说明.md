# 水獭星球 · 后端接入说明（AI 中转 + 生图 + 表单留资 + 埋点）

> 本文档给后端同学，整理需要后端接手的功能：**AI 调用中转（对话 + 生图）**、**水獭蛋留存页表单**、**埋点上报**。
> 包含：接口约定、请求格式、当前前端实现位置、已知坑点，以及后端需要做的事。
>
> 🔒 **最重要的变化（务必先读第零部分）**：因为要公开上线，**前端已不再持有任何 AI key、不再直连 StepFun / 火山方舟**。
> 所有 AI 调用改为「前端 → 后端中转 → 上游」。两个 key 现在归后端保管，放后端环境变量。

# 第零部分 · ⚠️ AI 调用已改为后端中转（必读）

## 背景
公开上线时，任何打进前端 JS 的 key 都会暴露在浏览器、被人 F12 偷走盗刷。所以前端已改造：
- 不再有 `VITE_STEPFUN_API_KEY` / `VITE_ARK_API_KEY`（已从前端移除）。
- 前端改为请求**两个后端中转端点**（地址由后端提供，填进前端 `.env` 的 `VITE_CHAT_RELAY_URL` / `VITE_IMAGE_RELAY_URL`）。
- 两个上游 key（StepFun、火山方舟）现在**只放后端**，由后端调上游时附带。

> 两个 key 的真实值我会单独给你（也在前端 `.env` 注释里留了一份备查）。**不要再放回前端**。

## 后端要建的两个端点

### ① 对话中转（NPC 对话 / 月亮向导讲故事）—— ⚠️ 必须 SSE 流式透传
| 项 | 值 |
|---|---|
| 前端调用 | `POST <VITE_CHAT_RELAY_URL>`，body `{ "messages": [...] }`（**不带 key**） |
| 后端要做 | 收到 messages → 补 key + `model:"step-2-16k"` + `stream:true` 调 StepFun → **把 StepFun 的 SSE 响应原样透传回前端** |
| 上游 | `POST https://api.stepfun.com/v1/chat/completions`，Header `Authorization: Bearer <StepFun key>` |
| 上游 body | `{ "model":"step-2-16k", "messages":<前端传来的>, "stream":true }` |
| 响应 | **流式**：`Content-Type: text/event-stream`，逐行 `data: {...}`，前端读 `choices[0].delta.content` 累加。**不能等全部生成完再返回**——前端靠逐字显示打字机效果。 |

`messages` 结构：`{ role: 'system'|'user'|'assistant', content: string }[]`。第 0 条是 NPC 人设 system prompt（前端组装好发来），后面是往返历史。后端**原样转发即可，不要改 messages**。

> 透传要点：后端把上游 response body 的字节流直接 pipe 给前端响应即可（Node 里 `upstream.body.pipe(res)` 或逐 chunk 转发），保持 `data:` 行格式不变。前端解析逻辑（`stepfunChat.ts` 的 reader 循环）不变。

### ② 生图中转（探险相册）
| 项 | 值 |
|---|---|
| 前端调用 | `POST <VITE_IMAGE_RELAY_URL>`，body `{ "prompt": "...", "image": ["url1","url2"], "size": "2K"\|"2048x2048" }`（**不带 key**） |
| 后端要做 | 补 key + 固定参数调火山方舟 → 返回 `{ "url": "<生成图 url>" }` |
| 上游 | `POST https://ark.cn-beijing.volces.com/api/v3/images/generations`，Header `Authorization: Bearer <火山方舟 key>` |
| 上游 body | `{ "model":"doubao-seedream-5-0-260128", "prompt":<前端传来>, "image":<前端传来>, "size":<前端传来>, "sequential_image_generation":"disabled", "response_format":"url", "stream":false, "watermark":false }` |
| 响应 | 返回 `{ "url": "..." }`（前端兼容 `{url}` 或原样透传 ARK 的 `{data:[{url}]}` 两种）。 |

> 前端只发 `prompt / image / size` 三个变量，**`model / watermark / response_format` 等固定参数由后端补**（见上游 body）。

## 演示兜底（中转没好也能本地演示）
前端 `.env` 里 `VITE_CHAT_RELAY_URL` / `VITE_IMAGE_RELAY_URL` 留空时，会请求占位地址 `/api/chat` / `/api/image-gen`，请求失败 → **对话走友好兜底文案、生图槽位显示"生成失败可重抽"，不会崩**。后端端点 ready 后把真实地址填进前端 `.env` 重新打包即可。

# 第一部分 · 探险相册 AI 生图 —— 上游调用细节（供中转参考）

> ⚠️ 前端已不再直连火山方舟（改走第零部分②的中转）。本部分保留**上游 ARK 的调用细节 + prompt 拼装逻辑**，供后端写中转时参考。
> 前端实现集中在 [`src/lib/GalleryContext.tsx`](src/lib/GalleryContext.tsx)。

## 一、上游接口与模型一览

| 项 | 值 |
|---|---|
| 服务商 | 火山引擎方舟 **Ark**（豆包 **Seedream**） |
| 接口地址 | `POST https://ark.cn-beijing.volces.com/api/v3/images/generations` |
| 模型 | **`doubao-seedream-5-0-260128`** |
| 鉴权 | Header `Authorization: Bearer <火山方舟 key>` —— **由后端中转附带，不在前端** |
| 返回方式 | 非流式，`response_format: 'url'`，返回图片 URL |
| 前端实现位置 | `GalleryContext.tsx`：`genOne()`（现在发给中转，不带 key） |

## 二、尺寸常量（前端传给中转的 size 值）

```ts
const WIDE_SIZE   = '2K';          // 横图（右侧大图用）
const SQUARE_SIZE = '2048x2048';   // 方图（左侧缩略图用，正方形 1:1）
```

## 三、上游请求格式（后端中转补 key 后这样调 ARK）

```ts
POST https://ark.cn-beijing.volces.com/api/v3/images/generations
Headers:
  Content-Type: application/json
  Authorization: Bearer <火山方舟 key>     // ← 后端补，前端不带
Body:
{
  "model": "doubao-seedream-5-0-260128",   // 后端补
  "prompt": "<前端传来的 prompt>",
  "image": ["<参考图1 url>", "<参考图2 url>"],   // 前端传来
  "size": "2K" | "2048x2048",                    // 前端传来
  "sequential_image_generation": "disabled",     // 后端补
  "response_format": "url",                       // 后端补
  "stream": false,                                // 后端补
  "watermark": false                              // 后端补
}
```

**返回解析**：取 `data.data[0].url`，后端可包装成 `{ url }` 返回前端。

## 四、prompt 是怎么来的（不是写死一句，是拼出来的）

prompt = `STYLE_PREFIX（彩铅童趣风前缀）` + `场景描述` + `构图收尾句`，四个槽位各一套。

| 常量 | 位置 | 作用 |
|---|---|---|
| `STYLE_PREFIX` | 约 `GalleryContext.tsx:50` | 通用彩铅风前缀，每条 prompt 都拼在最前 |
| `WIDE_COMPOSITION` / `SQUARE_COMPOSITION` | 约第 55-65 行 | 横图 / 方图的构图收尾句 |
| `SLOT_SCENES` | 约第 60-100 行 | 四槽（npc1 / npc2 / fakeMoon / npc3）各自的场景描述 + 参考图组合 |
| `SLOT_CONFIG` | 约第 90-100 行 | 由上面拼出每槽的 `widePrompt` / `squarePrompt` |
| `REF` | `GalleryContext.tsx:41-46` | 5 张参考图（定妆图）的公网 URL |

横图、方图用**同一段场景描述**，只是构图收尾句不同（横版 vs 正方形两角色居中）。

## 五、四个槽位与触发时机

| 槽位 key | 内容 | 参考图 | 触发点（SectionParkour.tsx） |
|---|---|---|---|
| `npc1` | 林中初遇啄木鸟 | otter + woodpecker | 第 1 个 NPC 对话关闭 |

## 六、⚠️ 已知不稳定点 & 后端要做的「稳定一点」

> 以下都是实测踩过的坑，代码注释里也有记录（`GalleryContext.tsx:4-7` 和 `106-114`）。后端接手前务必读。

### 1. 参考图必须是「国内可稳定下载的公网 https」
- **不能用 `raw.githubusercontent.com`**：火山服务器在国内（cn-beijing），拉 raw 会超时（实测返回 400）。
- 现在用的是 **jsDelivr CDN 镜像**（`cdn.jsdelivr.net/gh/...`，实测火山可稳定下载）。
- 后端如果改成自己存参考图，要保证图源在国内可稳定、快速下载。

### 2. ARK 拉参考图约 25% 随机超时 → 必须保留重试
- ARK 拉参考图是间歇性随机 timeout（任何一张、含最小的图都会偶发挂，失败率约 25%，与文件大小无关），且 ARK ~10s 就快速判超时返回。
- 现在前端靠 **5 次退避重试**（`genWithRetry()` 第 148-159 行）把全挂概率压到约 0.1%；每次仍带 90s 超时兜底。
- **后端中转后一定要保留重试逻辑**，否则 8 张图/轮（4 槽 × 2）平均会坏约 2 张。

### 3. ✅ key 已移出前端（生图已走中转）
- 前端已不再直连火山、不再持 `VITE_ARK_API_KEY`，改走第零部分②的生图中转。
- **后端核心任务**：实现该中转端点——收前端的 `{ prompt, image, size }`，补 key + 固定参数调 ARK，返回 `{ url }`，并在服务端做好重试/超时/key 保管。

# 第二部分 · 水獭蛋留存页表单（邮箱 / 微信号）

> 结算页「珍藏回忆」→ 水獭蛋留存页，用户领蛋后可留联系方式。**中英分流**：英文留邮箱，中文留微信号。
> 全部实现集中在 [`src/components/SectionEgg.tsx`](src/components/SectionEgg.tsx)。

## 一、接口约定一览

| 项 | 值 |
|---|---|
| 方法/路径 | `POST <后端提供的 URL>` |
| 端点配置 | 环境变量 `VITE_EGG_SUBMIT_URL`（`SectionEgg.tsx:6`），未填则占位 `/api/otter-egg` |
| 请求头 | `Content-Type: application/json` |
| 实现位置 | `submitContact()` 第 68–99 行 |
| 前端判定成功 | 只看 `res.ok`（2xx）（`SectionEgg.tsx:96`） |

## 二、请求体（按 lang 分流，两种都要能接收存储）

```ts
// SectionEgg.tsx:88-90
// 英文用户（留邮箱）
{ "email":  "user@example.com", "lang": "en", "source": "otter-egg", "ts": 1730000000000 }
// 中文用户（留微信号）
{ "wechat": "用户填的微信号",     "lang": "zh", "source": "otter-egg", "ts": 1730000000000 }
```

| 字段 | 说明 |
|---|---|
| `email` / `wechat` | 二选一（按 `lang`）。英文带 `email`，中文带 `wechat` |
| `lang` | `"en"` / `"zh"`，标记语言来源 |
| `source` | 固定 `"otter-egg"` |
| `ts` | 毫秒时间戳（`Date.now()`） |

## 三、响应约定

- 成功：返回 **2xx**。
- 失败：返回**非 2xx**；有频率限制建议 **429**（前端会提示「稍后再试」）。
- 前端不解析响应体，只看 HTTP 状态码。

## 四、校验现状（后端不要做错误假设）

| 语言 | 字段 | 前端校验 |
|---|---|---|
| 英文 | email | 正则校验合法格式（`EMAIL_RE`，`SectionEgg.tsx:14`） |
| 中文 | wechat | **只校验非空**（微信号无标准格式，可能是中英文/手机号/字母） |

> 后端**别假设 wechat 有固定格式**，按字符串原样存。建议落库去重。

## 五、⚠️ 部署前必改：关掉演示开关

```ts
// SectionEgg.tsx:8
const DEMO_MODE = import.meta.env.VITE_EGG_DEMO === 'true';
```

- 现在 `.env` 里是 `VITE_EGG_DEMO="true"` —— **提交会跳过真实请求、直接假成功**（`SectionEgg.tsx:81`），方便端点没好时也能完整演示「领蛋 → 留资 → 成功」。
- **后端端点 ready 后必须**：
  1. 把 `VITE_EGG_DEMO` 改成 `false`（或删除）；
  2. 把真实地址填进 `VITE_EGG_SUBMIT_URL`。
- 否则前端永远不会真的发请求给后端。

## 六、隐私合规（归后端 / 产品）

- 收集的是**儿童家长联系方式**，需注意隐私政策、退订 / 删除入口等。
- 微信号目前需人工添加（种子期人工运营，无公众号）；邮箱后续可批量群发。

# 第四部分 · 部署 / 静态资源服务建议（性能）

> 前端资源已做过一轮瘦身（3D 模型 Meshopt 压缩、图片转 WebP、删废文件），构建产物从 ~338MB 降到 ~8MB。
> 下面是部署时服务端可再叠加的优化，能让二次访问几乎秒开。归后端 / 运维。

## 一、开启 Brotli / gzip 静态压缩

- 对 `.js` / `.css` / `.json` / `.glb`（Meshopt 后的二进制）开启 Brotli（优先）或 gzip。
- `.webp` / `.png` 已是压缩格式，再压意义不大，可不压。
- Nginx 示例：`brotli on; brotli_types application/javascript text/css application/json model/gltf-binary;`

## 二、缓存头（静态资源带 hash 文件名，可长缓存）

- Vite 构建出的 `assets/*.js|css` 文件名自带 content hash，内容变则文件名变 → 可设 `Cache-Control: public, max-age=31536000, immutable`。
- `public/` 下的 glb / webp（文件名固定、无 hash）：建议中等缓存（如 `max-age=86400`）或上线时手动刷新 CDN。
- `index.html` 不缓存或短缓存（`no-cache`），保证用户拿到最新入口。

## 三、glb 解码说明（避免踩坑）

- 模型用 **Meshopt** 压缩，解码器已随 three/drei 打包进前端 JS，**不依赖任何外部 CDN** —— 国内用户不会被墙卡住。
- ⚠️ 不要改成 Draco：drei 的 Draco 解码器默认从 `gstatic.com` 拉，国内会超时。当前没用 Draco，保持现状即可。

## 四、首屏 JS 体积（如后续仍嫌慢）

- 当前 three.js 相关代码打进单一主包（~1.4MB，gzip 后 ~398KB），首页即加载。
- 若要进一步优化首屏，可把跑酷 3D 场景（ParkourScene）用 `React.lazy` 拆成独立 chunk、滚到该页才加载。本次未做（体积问题已基本解决），属可选项，需回归测试。
